Leftover Clock — App Map

A take-home guide to where things live. Home leftovers in opaque containers get a "first seen" date from fridge photos alone: take a photo, the app finds each container, matches it to the earlier photo, and pins its age.

The main pieces

Screens (phone)Next.js pages under app/: Fridge List, Fridge View with pins, Add Photo, timelines.
Matching clientlib/matching-client.ts sends the photos to the server and maps the answer back to stored containers.
Gemini routes (server)app/api/match and app/api/search call server/gemini.ts. The API key never leaves the server.
Storage (phone)IndexedDB through Dexie (lib/db.ts, writes in lib/actions.ts). The server stores nothing.
Evaluationeval/run-eval.ts runs the same matcher on real photo pairs and scores it against hand-confirmed answer keys in eval/truth/.

One action: adding a photo

Reference route (3 stops)

Search for the anchor in your editor; line numbers drift.

  1. Entry: the "Start matching" button
    app/fridges/[fridgeId]/add-photo/page.tsx → async function start()
    Refuses a photo dated before the fridge's latest photo or in the future (olderThan, future), shows the reminder cards while waiting, then calls matchAndSave. On failure it shows PhotoCheck; nothing is saved.
  2. Logic: two-step matching
    lib/matching-client.ts → matchAndSave, and server/gemini.ts → mapPrompt, searchPrompt, generate
    Step 1 maps the new photo against the previous one's containers (short aliases c1, c2, …). Step 2 searches for every container step 1 missed, by its close-up crop. generate retries once on "busy" and never falls back to a weaker model.
  3. Result: saved and pinned
    lib/actions.ts → applyMatch, then app/fridges/[fridgeId]/page.tsx with components/PhotoMap.tsx and components/UnseenShelf.tsx
    Saves the photo, one crop and sighting per container, and new containers dated to the photo. The Fridge View reads the latest photo live and pins each container's age; containers not seen go to the Unseen Shelf.

A practice to reuse: measure a model on photos it was never tuned on

What was done. Prompts were tuned on one photo pair (10/22 → 10/23) and frozen in commit 5da96af. Two later pairs were held out. Each held-out answer key was drafted from one matcher run, confirmed box by box against both full photos, and saved in eval/truth/ before the scored run. Correct links, misses, and wrong links were counted separately, because a wrong link silently gives a container someone else's date.

What the evidence showed. The tuning pair scored 19–20 of 23 with about 1 wrong link per run. The held-out pairs scored 27 of 43 with 14 wrong links (eval/results/heldout-2026-10-26.json; table in the README). In the fridge reorganized overnight, the model placed several boxes near where containers used to be. Tuning-set numbers alone would have overstated the matcher, and they are why the one-tap fixes are part of the core flow.

How to reuse it. For any model-backed feature: freeze the prompt and model, keep test cases the tuning never saw, fix the answer key before you score, and count each kind of error by what it costs the user instead of one combined accuracy.

Run it again

npm install, put GEMINI_API_KEY=… in .env.local, then npm run dev and open http://localhost:3000. Re-print the held-out table without API calls: npx tsx eval/run-eval.ts --rescore eval/results/heldout-2026-10-26.json.
